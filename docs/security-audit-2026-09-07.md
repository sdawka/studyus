# Security audit — 2026-09-07

Scope: Studyus browser → Astro middleware/API → services → D1/R2/LearnerAgent → integrations and deployment configuration. This is an audit, not a remediation or release. Application behavior, dependencies, and security configuration are unchanged. Findings distinguish local reproductions, source-confirmed gaps, and unverified deployed exposure.

## Decisions first

These are recommendations and working assumptions, not newly approved product decisions.

1. **Treat uploaded documents as hostile.** Recommend downloads for active content, or previews on a separate origin with a restrictive sandbox. A learner owning an upload does not make its contents trustworthy: a malicious document may come from elsewhere.
2. **Require rejected mutations to leave no persistent effects.** Validate all ownership and invariants before writing, then atomically commit related D1 rows. This is a security boundary as well as a recovery guarantee.
3. **Define account-wide resource budgets.** Recommend enforceable AI spend, upload storage, and ingestion limits; browser/session IDs are not trustworthy quota identities. Current per-message/per-file/per-session limits do not establish an account-wide ceiling.
4. **Keep bearer calendar sharing explicit and revocable.** Assume anyone possessing the subscription URL is authorized to read its projected calendar. Retain the existing warning/rotation, and verify that logs and traces do not retain those credentials unnecessarily.
5. **Use a separate development learner for authenticated QA.** The requested Clerk Agent Tasks feature was exercised through its Backend API because no task-capable Clerk MCP is available; successful task creation is not equivalent to browser authentication. See the final authenticated-testing ledger for the mechanism actually used. Security proofs remain local and synthetic; no production security probes are authorized.

6. **Define account deletion and external revocation semantics.** Recommend revoking calendar feeds and coordinating D1/R2 cleanup when Clerk accounts are deleted, rather than assuming provider deletion erases app-owned data. Clerk Account Security exposes Delete account; deletion itself was deliberately not executed.

## Threat model and attack surfaces

| Asset / journey | Actor and trust boundary | Enforcement examined |
| --- | --- | --- |
| Learner identity, email, settings, recovery | Anonymous browser → Clerk → immutable local user ID | Middleware, local-user resolution, retired password endpoints; live provider recovery policies remain outside verified scope |
| Courses, KCs, notes, tasks, grades, study history | One authenticated learner → another learner's IDs | API schemas, ownership services, D1 predicates and mutation ordering |
| Tutor transcripts, mastery and AI spend | Browser input → per-learner Durable Object → provider → D1 projection | Runtime identity, turn acceptance/caps, failure/cancellation and provider request construction |
| Uploaded files | User-supplied bytes/MIME/name → D1 metadata + R2 → same-origin browser response | Ownership before object access, size limit, response headers and cleanup ordering |
| Calendar and provider access | Learner → Clerk OAuth token broker → Google/Microsoft; public feed token → private projection | Connection ownership, provider URL construction, outbox/retry logic, hashed rotating feed credentials |
| Public funnel analytics and operational budget | Unauthenticated caller → schema → D1 → PostHog | Batch/session limits, event-ID deduplication, DNT, caller-controlled conversion claims |
| Deployment and secrets | Developer/CI dependencies → build → Worker bindings; operators → logs/traces | Tracked configuration, lockfile consumers, workflow privileges, narrow secret-pattern scan; read-only Worker/domain/TLS metadata; remaining remote policies unverified |

The application model exposes a learner role, not an organization/admin permission hierarchy. Internal bindings and Clerk Backend API credentials are privileged boundaries, not public authentication mechanisms. Public surfaces are marketing/trial routes, anonymous demo ingestion, sign-in/up and tokenized calendar feeds. The route inventory contains 66 API files; this is an inventory count, not a claim of 66 individually exercised endpoints.

## Findings

### S1 — Active uploads are served as same-origin HTML

**Confirmed same-origin script execution in a local authenticated browser. Priority P1, conditional high impact, high confidence in execution.** A learner who uploads a malicious HTML document and opens its attachment URL receives browser-interpretable HTML inline on the app origin. Ownership prevents another learner from simply opening the attacker's upload, so this is not a demonstrated cross-account stored-XSS channel. The realistic prerequisite is persuading a victim to upload/open an attacker-supplied file; account self-XSS alone has lower severity.

Evidence: `src/lib/services/attachments.ts:35–43` retains caller MIME; `src/pages/api/v1/attachments/[id].ts:15–16` returns it with inline disposition. `tests/security-input.audit.test.ts` stores a harmless script-bearing HTML fixture in real local R2/D1 and observes `text/html`, inline disposition and no `nosniff`. Reproduce locally as an owner with `new File([...], 'active.html', {type:'text/html'})`, then invoke the actual attachment GET. The authenticated browser then uploaded `synthetic-safe-upload.html` through Class notes, opened its returned link, and observed `document.title === "AUDIT_EXECUTED"` at `/api/v1/attachments/[id]`. [Sanitized browser evidence](audit-evidence/2026-09-07/authenticated-evidence.json), [uploaded file UI](audit-evidence/2026-09-07/security--html-upload-listed.png), [opened file](audit-evidence/2026-09-07/security--html-attachment-executed.png). No session theft or external callback was attempted. The expected-failure header test records the proposed forced-download policy; a separately validated isolated-preview solution would require replacing that policy-specific assertion with its own browser safety regression.

Recommend forced downloads for untrusted active types, safely encoded filenames and `nosniff`, or a separate sandboxed preview origin. Acceptance: uploaded HTML/SVG cannot execute in the application origin; foreign GET/DELETE remains 404 with metadata and object unchanged. Effort: 0.5–1 day; separate preview architecture is larger.

### S2 — Rejected task/assessment mutations still change persistent state

**Confirmed, medium integrity impact, high confidence; P1 correctness / P2 exploitation.** An authenticated owner can create or change their own task/assessment with a foreign or missing linked ID. The request throws `NotFoundError` (mapped to 404), but the parent insert/update has already happened. An attacker needs no valid foreign ID: a nonexistent UUID triggers the same ordering. This does not grant another learner's data access; repeated rejected creates can grow self-owned rows, and rejected grade updates can diverge from subsequent mastery processing.

Evidence: `src/lib/services/tasks.ts:81–102,109–138` and `assessments.ts:58–75,120–146`. Four real-D1 regression cases in `tests/security-authorization.audit.test.ts` cover rejected task creation, assessment creation, task update and assessment update. Reproduce using an owned course/KC plus a foreign link: create receives a rejection yet leaves a row; update receives a rejection yet changes title/completion or grade.

Recommend validating every reference before the first write, then batching related writes atomically. Acceptance: on rejected ownership/reference checks, parent rows, links, derived events/tasks and mastery remain exactly unchanged; retries do not accumulate rows. Effort: 0.5–1 day across the four paths and regression promotion.

### S3 — Telemetry quotas race, reset with arbitrary identities and accept forged conversions

**Confirmed application boundary gap, medium integrity/cost impact, high confidence; P2.** No authentication is required. The caller chooses session and event UUIDs and may claim `onboarding_completed`; the 100-event cap is per caller-chosen session. This changes funnel telemetry, not actual learner onboarding. D1 growth is reproduced; PostHog cost propagation is source-traced, not sent in the proof. Unknown deployed edge limits affect practical volume.

Evidence: `src/pages/api/public/demo-events.ts:11–26`, `src/lib/services/demoFunnel.ts:7–42`. `tests/security-public-ingestion.audit.test.ts` makes five 20-event batches, confirms event 101 on that session is refused, changes only the synthetic session UUID and persists another event: 101 claimed completions total. Separate tests confirm oversized batches leave no rows and replayed event IDs are not duplicated. A separate real-D1 concurrent test starts with 80 rows and sends two 20-event requests together: the stored count exceeds the existing 100-event cap. Its desired invariant is expected-failing. No load test or third-party delivery was performed.

Recommend rate controls independent of caller-minted IDs, a bounded trial credential where useful, an atomic quota, and separating untrusted interaction telemetry from server-confirmed business conversions. Acceptance: concurrent requests and fresh session IDs cannot reset the chosen allowance; denied requests write no D1 rows or analytics jobs; conversions used as authoritative are produced by the backend. Effort: 1–2 days. The current passing quota demonstration is a characterization test and must be replaced with the selected policy's denial regression during remediation.

### S4 — Account-wide AI, storage and background-work ceilings are not established

**Source-confirmed missing application controls; deployed abuse unverified, potentially high economic impact; P1 decision / P2 implementation.** A signed-in learner can open fresh tutor conversations, upload many individually valid files and generate revision-specific calendar work. Self-service signup and absent external quotas increase exploitability; provider account quotas were not verified. Read-only deployed Worker settings show `AI_FEATURES_ENABLED=true` but no `OPENROUTER_API_KEY` binding: paid AI abuse is therefore conditional on enabling provider access, not a demonstrated current production exposure.

Tutor: `src/lib/runtime/tutorRuntime.ts:139–145,247–251` enforces 30/60-message conversation caps but creates new conversations without a user/time budget. `src/lib/services/tutor/openrouter.ts:27–53` has no output-token ceiling or request deadline. Attachments: `courses/[id]/attachments.ts:10` materializes multipart input before the 10MB service check; no account byte/count ceiling found. Calendar: `calendarOutboxProcessor.ts:336–337` selects a global batch of 100 and `calendarScheduled.ts:20` processes it every five minutes; completed rows are marked done without a pruning path found. Sustained one-user backlog/fairness failure was not reproduced.

Recommend explicit per-user rolling usage and concurrency limits, provider output/deadline limits, upload quotas and bounded parsing, fair calendar batching plus retention. Acceptance: rejected work makes no provider call/object/write; concurrent requests share the same allowance; one user's backlog cannot starve another; completed outbox history is bounded. Effort: 2–4 days after product budget decisions. No destructive resource-exhaustion proof was attempted.

### S5 — Resource links allow non-web schemes

**Confirmed validation gap; browser exploit and cross-user delivery unverified, low-to-medium severity; P2.** `src/lib/schemas/resources.ts:15` uses `z.url()` and accepts `javascript:`, `data:` and `file:`. ResourceTile/ResourceCard send those values to anchors and `window.open`; source/built setter inspection found no scheme allowlist. Links remain owner-scoped, so do not infer a cross-tenant XSS route. Browser handling of these schemes varies.

Evidence: `tests/security-input.audit.test.ts` parses the three synthetic schemes successfully; desired HTTP(S)-only acceptance is expected-failing. Recommend allowlisting `http:`/`https:` at persistence and navigation boundaries and reviewing existing values. Acceptance: rejected schemes cause no persisted resource or executable navigation; ordinary HTTPS links continue working. Effort: 0.5 day. This schema-level test does not establish browser execution.

### S6 — Cross-store failures can orphan files or provider calendars

**Source-confirmed ordering risk, runtime failure injection not performed; medium reliability/cost impact, medium confidence; P2.** `attachments.ts:35–37` writes R2 before inserting D1; deletion removes R2 before D1. A database failure between operations leaves an orphan object or stale metadata. D1 foreign-key cascades do not remove R2 objects. `calendarConnect.ts:86,121,154` may create the external calendar before local persistence; retries discover owned calendars through local records, so a persistence failure can leave a provider orphan. No provider mutation failure was induced.

Recommend compensating deletes or durable reconciliation with stable operation IDs; avoid implying a distributed transaction. Acceptance: forced persistence failure removes/reconciles newly created objects; retry cannot duplicate remote calendars; deletion and account cleanup drain owned objects. Effort: 1–2 days plus provider sandbox verification.

### S7 — Account deletion is not connected to app-owned data/feed cleanup

**Source-observed lifecycle gap with browser-confirmed Delete account availability; deletion consequences unverified, medium privacy risk; P2.** `src/pages/account/[...path].astro` embeds Clerk UserProfile. No `user.deleted` webhook or app user-deletion service was found in the route/source search. Public calendar credentials resolve against D1 alone (`calendarFeed.ts:39–52`), bypassing Clerk. If the exposed account deletion is used without out-of-repository cleanup, its bearer feed may remain readable and private D1/R2 data may remain retained. A deleted identity cannot use the authenticated revoke endpoint. This was not reproduced by deleting a provider account.

Recommend an idempotent verified deletion-event flow with an explicit retention policy, immediate feed revocation and coordinated R2 cleanup; document failure recovery. Acceptance: a synthetic deletion event cannot be forged/replayed to delete another account, and a legitimate deletion revokes its feed and schedules/completes the intended data cleanup; failures retry safely. Effort: 1–2 days plus provider sandbox validation. Remote webhook/dashboard configuration remains unknown.

## Configuration and operational hardening

- Local HTML and 401 responses lacked CSP, frame protection, `nosniff`, and explicit private/no-store cache policy in the sampled responses. Source has no common header policy; successful calendar feed responses do set private/no-store. **Hardening recommendation, not a demonstrated deployed cache leak/clickjacking exploit:** establish a compatible header policy, exercise Clerk and inline scripts, and verify production edge headers. Acceptance: private responses cannot enter a shared cache; framing policy and CSP work with legitimate flows. Effort: 1–2 days.
- `src/lib/apiErrors.ts` logs complete unexpected errors; OpenRouter errors include up to 500 characters of upstream response text; calendar failures retain error messages (the calendar provider wrappers omit response bodies). **Sensitive logging risk:** use structured codes and redacted diagnostics. No production logs or actual personal-data leakage were inspected. Acceptance: synthetic provider/DB errors containing secret markers never put those markers in retained logs. Effort: 0.5–1 day.
- Feed tokens occur in request paths and traces are configured. [Cloudflare trace documentation](https://developers.cloudflare.com/workers/observability/traces/) describes platform tracing; actual retained attributes/access controls were not inspected. Review telemetry retention and token redaction. Hashing in D1 does not protect copies in URLs/logs. Effort: 0.5 day.
- Resource cards load Google-hosted favicons for saved resource hostnames before navigation. This is a source-observed third-party disclosure of domains, not document contents; decide whether that is appropriate for private study materials, or use generic/local icons. Effort: 0.5 day.
- CI runs `npm ci`, types, Vitest, build and annotation checks. It does not run browser authentication/security checks or dependency auditing. Actions use version tags, and workflow token permissions are not explicitly narrowed. Repository/organization permission defaults, branch protection and Cloudflare Builds settings were not queried. Worker binding names/types were checked without exposing secret values. Recommend explicit least-privilege permissions, pinned actions and isolated auth/browser checks; no bypass/merge/deploy was performed. Effort: 1 day.
- A narrow scan of tracked working-tree text found no matches for private-key, Clerk-secret, OpenRouter-secret or GitHub-token patterns. It excluded Git history, ignored files, remote secrets and other credential formats. `.env.local`, `.env.*.local`, `.dev.vars`, Clerk browser state and test artifacts are ignored. This is limited evidence, not a complete secret audit.

Read-only Cloudflare management evidence on 2026-09-07 mapped `studyus.app` to Worker `studyus`, production. Latest deployment metadata was September 1, 00:12:36 UTC, version `c1453ebe-ca37-40d4-ae92-623c003112c4`; source/deployment parity was not established. Bindings include D1, R2, LearnerAgent, Clerk and PostHog; the OpenRouter key is absent. Observability reports global enabled=false, logs enabled=false, traces enabled=true and redact_query_string=false; actual collection, retained records and access were not inspected.

**Transport hardening recommendation (P2, 0.5 day):** zone settings report minimum TLS 1.0, Always Use HTTPS off, HSTS disabled and SSL mode Full. Recommend TLS 1.2 minimum and deliberate HTTPS/HSTS rollout after compatibility checks. Full versus Strict origin-certificate validation is relevant to conventional origins, not evidence of a Worker custom-domain flaw. No HTTP downgrade or TLS handshake attack was attempted. Acceptance: authorized verification confirms HTTP redirects and the selected TLS floor/HSTS policy without breaking authentication.

Zone entrypoint reads returned “could not find entrypoint ruleset” for rate limiting, custom firewall and response-header transforms. The zone lists managed normalization, free managed firewall and DDoS rulesets; listing alone does not establish their activation or effectiveness. Account-level rules, platform limits and other settings may still apply. This narrows the edge-control gap but does not prove unlimited requests or absent effective headers. All of these were management GETs, not production application security probes; no settings changed.
