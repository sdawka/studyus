## Decisions first

These are recommendations/working assumptions, not newly approved product decisions.

1. **Automatic scheduling or a recommended next move?** Recommend describing the implemented recommendation/manual-rescheduling behavior. The landing promises automatic movement into free time, but the inspected runtime has no matching general replanner. Building one would be a separate architectural decision, not copy polish.
2. **Sample demonstration or personalized preview?** Recommend keeping an explicitly named sample course separate from a learner's proposed course until recommendations actually use its topics. Currently custom course labels wrap fixed sample recommendations.
3. **Preserve the first-course and evidence boundaries.** Treat one active academic course with meaningful concepts as first-run success. Demo scores/actions must not become real grades, tasks, or mastery. Existing onboarding tests cover this boundary; browser import completion remains unverified.
4. **One canonical auth experience.** Recommend consolidating `/login` and `/sign-in` while preserving return destinations and demo handoff. The duplicate layouts already differ visibly.
5. **Protect work before polishing.** Prioritize the note-save race, then complete authenticated testing. Keep learning feedback informational; do not add guilt/streak mechanics to recovery flows.

Explicit audit scope is recorded in [decision_log.md](decision_log.md).

## Ranked findings

Effort estimates are engineering time including focused validation, excluding provider setup and release.

### F1 — P1: A stale save marks newer note edits saved

**Verified component defect; authenticated browser reproduction pending.** In [NoteEditor.svelte](../src/components/notes/NoteEditor.svelte#L112), `saveNote()` snapshots a PATCH payload, then clears `unsavedChanges` unconditionally after success. Inputs remain editable while waiting. The deferred-response test sends “Saved snapshot,” edits to “Newer unsaved draft,” resolves the older request, and observes disabled Save plus “Saved.” The newer text can be lost on navigation/reload.

- Affects notes editing from course/global notes, especially slow connections.
- Recommend tracking a draft revision per request, only marking the matching revision saved; serialize/coalesce overlapping saves. Preserve a retryable newer draft.
- Acceptance: edit B while save A is pending; A's response must not report B saved. Saving/reloading B preserves B. Failure retains content/links, retry succeeds, and out-of-order responses cannot regress saved state.
- Effort: **0.5–1.5 days**.
- Coverage: [NoteEditor.audit.test.ts](../tests/components/NoteEditor.audit.test.ts) reproduces the ordinary failure, retained as **one documented `it.fails`** because product fixes were prohibited. Green test execution does not mean this behavior is fixed. Convert to a normal passing test with the fix.

### F2 — P1: Personalized trial displays invented course-specific conclusions

**Verified in deployed browser and source.** Entering `AUDIT 101` with only momentum/conservation and dimensional-analysis topics produced “AUDIT 101 — Bernoulli equation,” with “the quiz is Friday” and two unlocking topics never supplied. [PublicTrial.svelte](../src/components/demo/PublicTrial.svelte#L38) hardcodes the scenarios; the recommendation card combines those with the active course code. All nine scenario action/payoff states were exercised; these are canned simulations, not evidence of backend adaptation.

- Affects first-run trust and the custom-course-to-preview journey.
- Recommend explicitly retaining the sample course for simulated decisions, or deriving a bounded preview from reviewed input. Keep importable course context distinct from sample evidence in the visible UI.
- Acceptance: a custom course never receives unsupported claims about its quizzes, weak topics, or prerequisites. The learner can identify the source of every displayed recommendation. Test manual and reviewed-template inputs, not only the default sample.
- Effort: **0.5–1 day** for clear separation; **several days** for input-derived behavior, requiring a product decision.

### F3 — P1: Landing promises exceed traced scheduling behavior

**Verified public claim; implementation-gap finding from source, not a completed runtime rescheduling test.** [FeatureReplan.astro](../src/components/marketing/landing/FeatureReplan.astro#L43) promises unfinished work moving into the next real opening. The demonstration is hardcoded. The inspected services generate/dismiss tasks and expose explicit manual session rescheduling; a general capacity-aware automatic replanner was not found. The trial's disrupted-week action says two sessions moved and a task dropped without exercising those real operations.

- Affects acquisition expectations and returning-user recovery.
- Recommend narrowing the claim to prioritization/manual planning until automatic scheduling has an executable contract.
- Acceptance: either copy accurately describes current behavior, or a real-D1/backend plus browser test advances past a missed task/session and proves collision-free, capacity-aware movement, deadline handling, user control, and idempotent retry.
- Effort: **2–4 hours** for copy clarification; **multi-day architectural work** for scheduling.

### F4 — P2: Duplicate auth layouts produce a visibly overflowing login card

**Verified deployed screenshots and DOM measurements.** `/login` nests Clerk's card inside a padded `.card` ([login.astro](../src/pages/login.astro#L100)). At 390px the outer card spans x=16–374, while Clerk spans x=41–391; document width is 391px. At 320px document width is 321px, and the form extends beyond its parent. Desktop also shows the offset nested-card shape. `/sign-in` and `/sign-up` fit at 390px and use a different dark marketing shell. Empty-email submission correctly focused the required field.

- Affects entry, return authentication, narrow screens and consistency.
- Recommend a shared canonical auth wrapper and destination handling. Add an accessible loading state: initial Clerk hydration showed a blank central region before the form appeared; no outage fallback was exercised.
- Acceptance: cards and controls fit their parent and viewport at 320/390/768/1280px, no duplicated page heading, keyboard validation remains usable, and auth/demo return URLs survive consolidation. Delayed/failed provider loading offers an intelligible state.
- Effort: **0.5–1 day**.

### F5 — P2: Trial setup omits persistent labels and selected-state semantics

**Verified DOM/AX and source.** Course search, code, title and topics fields have no associated labels or `aria-label`; placeholders carry the instruction. Guidance/depth buttons indicate selection through CSS only ([PublicTrial.svelte](../src/components/demo/PublicTrial.svelte#L305)). AX inspection exposed no selected state for these preference controls. A no-match search simply removes results without an empty-state explanation. Blank manual submission does show a useful inline message; long course titles wrapped within the reviewed-summary card at 390px.

- Affects assisted navigation, remembering field purpose, and unsupported-course recovery.
- Recommend persistent labels, radio-group or pressed-state semantics, and explicit no-results/manual-entry guidance. Add Back controls that preserve preceding setup choices.
- Acceptance: each input has a stable accessible name after entry; selected preferences are programmatically exposed; keyboard traversal and changing choices work; zero-result search announces a recovery path; returning to context preserves draft values.
- Effort: **0.5–1 day**. Browser labels/selection and no-results tests are still missing.

### F6 — P2: Mobile users lose the trial reset control

**Verified browser/source.** “Clear trial data” is present on desktop but hidden by the ≤1080px rule ([PublicTrial.svelte](../src/components/demo/PublicTrial.svelte#L495)); no replacement appeared in the mobile AX tree. Demo scores persisted across reload while the selected scenario returned to the first scenario. The persistent state is therefore easy to retain and harder to intentionally restart on mobile.

- Affects repeat previews, correcting setup and local-data control.
- Recommend a visible mobile reset/edit-setup action with appropriate confirmation and clear scope.
- Acceptance: users at 390px can find and reset the trial through the UI; reload confirms cleared state without affecting an authenticated account. Restore the current scenario or explain restart behavior.
- Effort: **2–4 hours**. Reset itself was not executed in the user's Chrome session.

### F7 — P1 coverage risk: Passing CI does not validate the main browser journeys

**Verified configuration.** [ci.yml](../.github/workflows/ci.yml) runs types, Vitest, build and static annotations. It does not run Playwright/layout checks. The authenticated config loads Clerk test credentials immediately; this checkout lacks them, so the suite fails before executing a browser test. Existing browser checks cover map hydration, tutor gating/end/reload, feed requests and layout, not the full onboarding/study/grade lifecycle.

- Affects confidence across all journeys; this is a test gap, not evidence those journeys fail.
- Added an auth-independent [public config](../playwright.public.config.mjs) and two public journey/overflow checks using the existing Playwright stack. They are not yet wired into CI.
- Acceptance: required CI runs public browser checks against the candidate build, plus dedicated seeded test-user journeys for onboarding, ownership denial, task/grade transitions, study completion/discard/retry and note recovery. Assert persisted results after reload. Keep provider-dependent smoke separately identifiable.
- Effort: **1–3 days** for core journey CI, plus authentication/provider setup.
